# 原稿の書き方（`_build/src/*.md`）

## ファイル名

`NN_名前.md`。`NN` は並べ順の目安（`00` はじめに、`10`〜`80` 本文、`90`〜 付録）。
**ファイル名が `9` で始まる原稿は「付録」扱い**で、用語ページの「本文で読む」の候補から外れる。
どのページに出すかは `site.json` の `pages[].src` で決まる（`pages` に書いていない原稿はビルドされない）。

## 本文ページの形

```markdown
---
docs: [doc1]                         ← このページで引用する資料（site.json の docs のキー）。出典欄と「原本を開く」ボタンになる
where: 発行者「資料名」p.3〜5        ← 題名の上の濃紺の札「原文の場所：…」
actors: [情報政策担当, ベンダー]      ← 題名の上の「読む人」の札（色は site.json の role_tags で決まる）
---

# 3. データの適切な管理               ← H1（画面の題名には site.json の seo が使われる。これは llms-full.txt 用）

導入文を1段落。ページ冒頭のリード文と、検索結果の説明に使われる。

## 3-まとめ このページの要点

- 3-1 1つ目の節の要点を1〜2文で。
- 3-2 2つ目の節の要点。            ← 番号は外され、つながった文章として濃紺の「SUMMARY」カードに出る

> 答えのボタン：ボタンの文字｜https://example.com/   ← 任意。答えの下にボタンを出す

{{原文 doc="doc1" id="data,data2"}}  ← source/ のブロックを差し込む（カンマで複数可）
```

### 節の見出しの規則

- `## <ページ番号>-<節番号> <題名>`（例 `## 3-1 情報そのものが狙われている`）。番号は目次・アンカー（`#s3-1`）になる
- `## <番号>-まとめ …` と `## <番号>-参考 …` は特別扱い（目次に出ない）
- 規則に合わない `##` は表示されない（`check_src.py` がエラーにする）

### 題名（site.json の pages[].seo）

`｜` と途中の `？` で改行され、1行目＝大きな題名、2行目＝シアンの副題、3行目＝灰色の資料名になる。
例：`家庭の備蓄は何日分？非常持出品のリスト｜みらい市 防災ハンドブック①`
`<title>` は `seo｜サイト名`。

### 題名の横に専用の画像を出す（任意）

フロントマターに `hero: assets/xxx.jpg|代替テキスト|リンク先URL`。このページだけ共通の横長の帯の代わりに使う。

### 導入文の下にボタンを置く（任意）

導入文の中に `<div class="app-cta">…</div>` を書くと、題名の下にそのまま出る。

## 原文ブロック（`_build/source/<資料>.txt`）

```
@@ data p=3
３．データの適切な管理

原文の段落。段落の間は空行。

・箇条は行頭の「・」「①」などをそのまま
| 表 | も |
|---|---|
| Markdownの | 表で書ける |

@@ data2 p=3-4                 ← ページをまたぐときは p=3-4
...
```

- 章ごとのファイル（`source/<資料>_1.txt` など）に分けて書いてもよい。全ファイルで id が重ならないよう、章ごとの接頭辞を付ける
- 1行1項目にする：`①…` のような小見出しは単独の段落に、`•` `✓` `⇒` で始まる行は1行ずつ空行で区切る（小見出しは太字、箇条は字下げで表示される）
- 図の中の文言は、PDFから抜いた語順が崩れていて照合できないことが多い。照合できる部分だけ表に組み直し、無理に入れない（解説の中で「著者が整理したもの」として要約する）
- `@@ <id> p=<ページ>`：id は英数字とハイフン。ページは PDF のページ番号（raw の `=== p.N ===` と同じ。ずれる資料は site.json の `offset`）
- 文言は PDF のとおり。直してよいのは、改行（PDFの折り返しをつなぐ）、箇条・表の体裁、脚注番号の削除だけ
- 表の列見出しは補ってよい（照合しない）
- 原文の中の「（１）」「【見出し】」など短い見出し行は太字になる（判定の正規表現は site.json の `genbun_heading_regex` で変えられる）

## 用語集（`pages` で slug が `glossary.slug`（既定 `yougo`）のページ）

```markdown
---
docs: [doc1]
where: 資料に出てくる用語
actors: [職員, ベンダー]
---

# 付録 用語集

導入文。

## API（えーぴーあい）{api}

最初の段落が「一言の定義」として一覧・検索・構造化データに使われる。

2段落目以降は用語ページだけに出る。

関連語：認可, レートリミット
```

- 見出しは `## 用語（よみがな）` または `## 用語（よみがな）{英字のslug}`。slug を省くと、よみをローマ字にしたものがファイル名になる（`yougo-api.html`）。ローマ字が重なるときは slug を付ける
- 用語は、英字を先、続けて五十音順に自動で並ぶ
- 3文字以上の用語は、本文の各節で最初の3つまで自動で用語ページにリンクされる
- 本文ページの SEO タイトルかキーワードの先頭が「〇〇とは」なら、用語ページは「〇〇の意味を一言で」に切り替わり、詳しい解説はその本文ページへ誘導する（検索での食い合いを防ぐ）

## 同義語（`_build/src/_同義語.txt`）

```
# 1行に、同じ意味として扱う語をカンマ区切り
多要素認証, MFA, 二要素認証
```

サイト内検索で、どれかの語で検索するとほかの語を含む節もヒットする。

## 書くときの注意

- 解説は「資料に書いてあること」と「著者の見解・補足」を区別する。資料に無い数字・日付・断定は、出典（`［n］` と `N-参考`）を付けるか書かない
- 1節の原文は長すぎないように（目安 1,500字以内）。長い章は節を分ける
- 「この節が答える質問」は、検索で実際に打たれそうな疑問文にする（AEO）
